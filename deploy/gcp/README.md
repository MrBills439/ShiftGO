# Deploying ShiftGO to Google Cloud

Everything runs in **London (`europe-west2`)** in the Google Cloud project
`pipcord`.

| Piece | Google Cloud service | Notes |
| --- | --- | --- |
| API (backend) | Cloud Run `shiftgo-api` | Scales to zero; HTTPS included |
| Web app | Cloud Run `shiftgo-web` | Forwards `/api/*` to the API |
| Database | Cloud SQL Postgres 16 `shiftgo-db` | Daily backups kept 7 days + point-in-time recovery |
| Photos, right-to-work files | Cloud Storage bucket `pipcord-shiftgo-uploads` | Private, versioned, mounted into the API at `/app/uploads` |
| Background jobs | Cloud Scheduler → `POST /internal/jobs/<name>` | Every minute / 5 min / daily; protected by a secret |
| Secrets | Secret Manager | Generated by the script; never in the code |
| Images | Artifact Registry `shiftgo`, built by Cloud Build | No Docker needed on your side |

**Cost, roughly £15–20 a month** at pilot size: almost all of it is the
database (smallest Cloud SQL size). Cloud Run, Scheduler and Storage are
pennies or inside Google's free allowance at this size.

## Before you start

1. Billing is turned on for the `pipcord` project
   (console.cloud.google.com/billing).
2. A [Resend](https://resend.com) account, an API key, and your sending domain
   verified in Resend (for example `leafrota.co.uk`).

## First deploy (about 20 minutes, mostly waiting for the database)

1. Open **Cloud Shell** (the `>_` icon at the top of console.cloud.google.com),
   with the `pipcord` project selected.
2. Run:
   ```bash
   git clone https://github.com/MrBills439/ShiftGO.git
   cd ShiftGO
   EMAIL_FROM="LeafRota <noreply@leafrota.co.uk>" ./deploy/gcp/deploy.sh
   ```
   The first deploy **requires** `EMAIL_FROM` (see "Email sender" below).
   If your project ID isn't literally `pipcord`, the script lists your projects;
   re-run with `PROJECT_ID=<id> ./deploy/gcp/deploy.sh`.
3. When asked, paste the Resend API key (it isn't shown on screen and goes
   straight into Secret Manager).
4. At the end it prints the **web app URL** and the **API URL** and checks both
   are healthy. Always use these URLs. Cloud Run also shows an older-style URL
   in the console; sign-in only works on the one printed here.

## Create your agency

```bash
./deploy/gcp/deploy.sh create-agency --name "Your Agency" --hr-email you@example.com --hr-name "Your Name"
```
Open the invitation email, choose a password, then set up two-step verification
with an authenticator app. Keep the backup codes.

## Email sender

Invitations and password-reset codes are sent through Resend:

- **Sender address:** the `EMAIL_FROM` setting on the `shiftgo-api` service
  (and the `shiftgo-admin` job), e.g. `LeafRota <noreply@leafrota.co.uk>`.
- **API key:** the Secret Manager secret `shiftgo-resend-api-key`. The script
  only creates it when it doesn't exist and never prints it.

How the sender survives deployments:

| You run | Sender used |
| --- | --- |
| `./deploy/gcp/deploy.sh` (service already deployed) | The one already on `shiftgo-api`. It is read before deploying and set again unchanged. |
| `EMAIL_FROM="…" ./deploy/gcp/deploy.sh` | The one you give (checked first: `Name <address@domain>` or `address@domain`). |
| First deploy without `EMAIL_FROM` | The script stops before changing anything and asks for it. |

Resend's test sender (`…@resend.dev`) is accepted with a warning: it only
delivers to your own Resend account address.

The same sender is applied to all three places that need it: the
`shiftgo-api` service, the `shiftgo-admin` job (invitations sent by
`create-agency`) and the `shiftgo-migrate` job. The deploy stops before
changing anything if:

- `EMAIL_FROM` on `shiftgo-api` is mapped from a Secret Manager secret (the
  script manages it as a plain setting and won't overwrite a secret mapping);
- the service exists but has no `EMAIL_FROM` (rerun with `EMAIL_FROM=…`);
- the service can't be read (permissions, network): this is never treated as
  a first deploy.

The script uses Cloud Run's *update* flags, so settings added by hand on the
services (for example Firebase secrets) are kept on every deploy. To check the
live sender without deploying:

```bash
gcloud run services describe shiftgo-api --region europe-west2 --format=json | grep -A1 '"EMAIL_FROM"'
```

These rules are tested in `deploy/gcp/test/email_from.test.sh` (stub `gcloud`,
runs in CI).

## Checking stored shift times (read-only)

```bash
./deploy/gcp/deploy.sh audit-shift-times
```

Runs `scripts/auditShiftTimes.js` in the `shiftgo-admin` job. It changes
nothing. It lists hand-entered shifts that fall in summer time (where the old
Schedule form stored times one hour late) and any rows whose `date` column
disagrees with their start time. Results are in the job's logs.

## Updating

Pull the latest code and run `./deploy/gcp/deploy.sh` again; the email sender
already in production is kept. It rebuilds,
runs any new database migrations, then switches traffic to the new version.
To roll back: Cloud Console → Cloud Run → the service → Revisions → send 100%
of traffic to the previous one.

## After the first deploy

- **Mobile app:** put the API URL into `mobile/eas.json` (`EXPO_PUBLIC_API_URL`
  for `preview` and `production`), then build the Android test APK.
- **Check the real-IP setting:** sign in with a wrong password once, then in
  Cloud Console → SQL → `shiftgo-db` → Cloud SQL Studio run
  `select key from "rateLimit";`. It should show *your* public IP. If it shows a
  Google address instead, set `TRUST_PROXY_HOPS` (API) / `TRUSTED_PROXY_HOPS`
  (web) to 2 in the script and redeploy.
- **Push notifications:** add the Firebase settings (`FIREBASE_PROJECT_ID`,
  `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY`) as secrets and to the API's
  `--set-secrets`; until then notifications are not sent.
- **Your own domain:** map `app.` / `api.` names to the services.
- **Restore test:** Cloud SQL → `shiftgo-db` → Backups → restore one into a new
  instance once, to prove backups work.
